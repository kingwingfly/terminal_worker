## Architecture and invariants

- The rules (owner's design, 2026-10-29): the kernel holds no command logic, and runs no commands: programs are user space's (crates/userland, the page). Every check is the kernel's, call by call; user space is untrusted, and only asks. Errors are errno, with coreutils' wording in the programs (`rm: cannot remove 'x': Permission denied`). New behaviour is a system call with its errno, or a program over the calls; never an endpoint. The API is `/api/sys`, the byte I/O (`/api/file`, `/api/pwrite`) and the events socket, nothing else.
- System calls (owner's design, 2026-10-29: the page is user space, the API its system calls; see README, Architecture): `crates/abi` is the interface, the calls (`Call`), their batch (`Batch`: the process's umask and sudo) and results, and errno with glibc's words; `crates/kernel` is the file system's syscalls, one function each, every check Linux's (namei, generic_permission with ACLs, sticky, protected links, ACLs as `system.posix_acl_*` xattrs), over the `Fs` store, tested on `MemStore`; `crates/worker/src/sys.rs` serves `POST /api/sys`, each call its own transaction. A call changes one name or inode, or fails and changes nothing; walking a tree is user space's. New file-system behaviour belongs in the kernel, as a syscall with its errno, never in a command the server runs.
- File descriptors (`crates/worker/src/fds.rs`, the `fds` table): `open`, `pread`, `pwrite`, `close` and `ioctl(FICLONE)` are system calls; a call may name an earlier call's descriptor (`{"ref": i}`, `sys::resolve`), and `pread`/`pwrite` carry up to 256 KiB as base64 in the batch, moved to or from R2 outside a transaction (`sys::bytes`); larger chunks stream on the Worker (`PUT /api/pwrite?fd=&index=`, files.rs), as `GET /api/file` reads them. Every batch keeps its session's descriptors (`fds::renew`, at most every 5 s per session, `sys::heard`); pages holding one say so every 8 s (web/http.mjs `hold`). A writer that gives no size writes in order: the file grows (`File::growing`), truncated as it opens, whole when it closes or when its writer is gone. Directories open to read (`O_DIRECTORY`); /proc is `procfs.rs`, and `/proc/self/fd/N` is a magic link followed in every call's paths (`sys::paths`). A descriptor is its session's (`auth::sid`: a signed-in session's key, or the browser's own `terminal_guest` cookie, which the Worker gives a browser at once, `lib.rs with_guest_cookie`). Uploads (web/upload.mjs), the editor's save, recordings (web/record.mjs, `O_APPEND`), `cp` (FICLONE) and the seed script write through them; nothing writes a file otherwise, but archive jobs, until processes (phase 5). A descriptor call stands as it ends, failed or not (sys.rs): a close that fails still closes.
- User space (`crates/userland`): the programs, as coreutils are (ls, stat, df, mkdir, rmdir, rm, mv, cp, ln, readlink, realpath, touch, chmod, chown, chgrp, getfacl, setfacl, getfattr, setfattr, fd, ps, kill), each an async function over `Sys` and nothing else; dates as GNU's (`time.rs`, UTC); ps and the shell's jobs read /proc (`procs.rs`); GNU's messages (`rm: cannot remove 'x': Permission denied`), silent on success but with -v; trees walked a level a batch (`walk::below`), never atomically. The page runs them (`Shell::program`, over `crates/frontend/src/sys.rs`); unit tests run them over the kernel in memory (`userland/src/tests.rs`). Names come from /etc/passwd and /etc/group, which the kernel generates as they are read (`sys::generated`). E2E tests reach the kernel through `tests/sys.js` (`sys`, `errno`, `mkdirp`, `rmrf`, `listing`, `entry`, `put`, a whole file written through a descriptor, and `program`, a small user space of the setup programs; `fakeKernel` for pages without a server).
- Core: pure Rust path resolution, the shell grammar (pipelines, xargs items, fd placeholders: `shell.rs`), text filters (`text.rs`), fd matching (`find.rs`), fuzzy completion, ranges, and the permission rules as provided methods of the `Store` trait (`permissions.rs`). `MemStore` implements it for tests; the worker's `Db` over SQLite. New file commands belong there, as validate-then-mutate methods, with MemStore tests.
- Frontend: Leptos tabs (`lib.rs`); each tab is a `shell::Shell` that runs pipelines stage by stage, and the programs of user space (`Shell::program`, `sudo_program`), whose questions (`mv -i`, `cp -i`) go to the tab's next line; xargs and fd -x run each command on its own, so each asks. web/app.js's `accountCommand` keeps the dialogs and hands the rest back to run as programs. Text filters, xargs and fd -x/-X run in the page. Browser bridge in web/app.js; chunked uploads in web/upload.mjs. CodeMirror loads lazily.
- Previews render in Rust: crates/frontend/src/viewer.rs mounts each into the viewer's content through `window.terminalPreview.show(content, path, kind, version)`, and app.js calls what it returns to release it; the mount happens only if `content.dataset.version` still names that open. app.js keeps the dialog shell, fullscreen, games, and focus handling. Markdown is sanitized with ammonia; maths is substituted after sanitizing.
- The viewer's search (`crates/frontend/src/search.rs`, the `Searchable` wrapper of text, code, diff and Markdown previews) matches Rust regular expressions over the DOM's text nodes and highlights them with the CSS Custom Highlight API, never changing the preview's markup; it searches again when the markup changes (code highlighting arrives later). It shows `#viewer-search` in the viewer bar while mounted, and its Esc must not close the viewer.
- crates/preview builds seven web workers (scripts/build.mjs): PDF (hayro), archive listings (zip, tar, flate2, with an expanded-byte budget; the main bundle has no archive code), diagram (merman, size profile), and four code groups (arborium). A loader whose wasm fails to load answers `[0, false, error]`, the failure of call 0 (ready); the page then stops that worker, so the next call starts a fresh one. Grammars are C: building needs clang with wasm32 and llvm-ar. Each worker file must stay under Cloudflare's 25 MiB asset limit; split a language group if one grows past it. The upload allowlist (core `kind`) must cover every previewable extension; a frontend test checks the highlighted languages.
- The AUTHORITY Durable Object named filesystem keeps all metadata in SQLite tables (`crates/worker/src/db.rs`). Every request's decisions and writes run in one `db::transact`, a hand-bound `transactionSync`: **never await inside it**. Do async work (reading the body, password hashing, rate limits) before, and re-check in the transaction what it relied on. A reply of 400 or more rolls back unless it is marked `keep()` (cleanups).
- **File bytes never pass through the authority.** The Worker (`files.rs`) asks it to authorize (`/internal/read`, `/internal/upload/begin|chunk`), streams R2 natively (no copying through wasm, `FixedLengthStream` for known lengths), then asks it to commit, which checks again. Downloads therefore never wait on uploads.
- Files have a fixed chunk size (8 MiB for chunked uploads; a single-request PUT is one chunk), so chunk i starts at i × chunk_size; the readable length of an uploading file is its contiguous committed prefix. A new file's node exists while it uploads; an overwrite swaps at completion only if the node still shows the file it replaces. Every chunk authorization, chunk commit and completion checks the destination again (`api::destination`): a new file where its node is now (it may have moved), while the uploader can traverse to it and owns it or may write it; an overwrite while the uploader may write the target that still shows its base.
- Storage: `nodes(path → ino)` are names, `inodes` hold owner, group, mode (with setuid/setgid/sticky), file id, link target and ACLs (JSON, core `acl`), `xattrs(ino, name, hex)`. `Store::set_node` with `ino` 0 makes an inode, otherwise updates that inode and names it; an inode goes with its last name. `Node.links` is computed (directories: 2 + subdirectories). The schema version is `meta.schema` (db::SCHEMA_VERSION); older local state is refused with a message to delete it, as nothing is migrated.
- Paths given to the Store rules are physical up to their last part: callers resolve with `Store::physical(who, path, follow)` (`commands::command_path` follows a final link, `entry_path` does not; API endpoints use `real!`). Physical resolution stops, leaving the rest as written, where the caller may not search or nothing is, so the rule that follows reports the usual error. protected_symlinks is enforced there; protected_hardlinks in `Store::link`; the sticky rule in `Store::unlinkable` (rm, rename, cp -f, ln -f).
- New nodes come from `permissions::created` (umask 022 or the parent's default ACL, setgid group inheritance); do not build `Node::file(who…, 0o644…)` for user-made files.
- Nodes refer to immutable file ids; copies share them. A store frees a file when no node refers to it, by putting its key prefix `chunks/<file>/` in `garbage` in the same transaction; the alarm lists and deletes everything under it (also objects written but never committed) and expires uploads idle for 24 hours. Home moves, mv and cp change metadata only.
- Every chunk write has its own R2 key (`chunks/<file>/<index>-<random>`, from `api::chunk_key`), and a chunk is committed once: a write sent again, late, or after completion is discarded, never overwriting bytes a reader, copy or completed file uses.
- The initialization marker (`system/terminal-authority-v2`) fails closed if the authority's storage disappears.
- Archive jobs are processes (owner's design, 2026-10-29; `jobs.rs`, `runner.rs`): `spawn {argv, cwd}` (zip, unzip, tar, faststart; ENOENT for anything else) starts one as the caller (root under sudo), owned by the account signed in, and gives a descriptor of its standard input (`/proc/PID/fd/0`), which unzip's answers are `pwrite`n to (`jobs::answer`); /proc/PID lists the account's (procfs.rs); `kill` signals one (its owner's or root's: EPERM, ESRCH), `wait {pid, since}` gives its state and what it wrote after `since` (waitid with WNOHANG, and a read of its output). sys.rs wakes the runner after spawn, an answer and kill. The shell follows a process it spawned (`Shell::follow`); `ps` and `kill` are user space's programs (userland `procs.rs`). `spawn` validates and snapshots the inputs in one transaction, pins the files they read (`job_files`, which garbage collection respects), then wakes a `JobRunner` (one per job, named by its id). The runner works from its alarm in bounded steps, keeps its plan in its own SQLite, and asks the authority for everything through `/internal/job/*`, a process's own way to the kernel, as the job's actor (re-derived each time; root only if started with sudo). Its container (`crates/jobs`) only reads and writes archives on its disk; bytes between R2 and it are streamed, never copied through wasm.
- Accounts are system calls (owner's design, 2026-10-29; sys.rs): `login`, `logout`, `sudo`, `passwd`, a signed-out `useradd` with a password, and an account's own `userdel` with its password run the kernel's handlers of them (api.rs `login`, `sudo`, `passwd`, `register`, `unregister`: rate limits, the KDF outside a transaction, the session cookie set on the batch's reply); root's `useradd`, `usermod`, `userdel`, `groupadd`, `groupmod`, `groupdel` are `commands::accounts`, given their options parsed by user space (crates/userland `accounts.rs`, as are whoami, id, groups and users, of /etc/passwd and /etc/group). web/app.js keeps the dialogs (su, login, logout, passwd, sudo -u/-k, a guest's useradd, an account's userdel of itself) and hands anything else back to the shell to run as a program (`{program: true}`). The server runs no commands; `/api/command`, `/api/login` and the rest are gone. Tests reach the account calls through `tests/sys.js` `api(request, name, {headers, data})`, answered with the statuses the endpoints had.
- Guests: `guest` is a real, locked account (uid/gid 65534, home `/guest`, `root:guest` 1777). A signed-out `useradd [-m|-M] [--short-password] NAME` (app.js's dialog; other options need sudo) makes an account with a private group, membership in guest, home `/guest/NAME` (made 700 with -m only, as useradd), and signs in; it is rate-limited ("register") and capped (`REGISTERED_MAX`). An account in group guest deletes itself (`userdel` with its password, app.js's dialog, for `userdel [-r] NAME` signed in as NAME), its password checked, by `commands::accounts::delete_account`, which root's userdel runs too: -r removes a home only if it is the account's own directory, and its same-name group goes unless another account is in it. A home not made yet is its account's alone to make (`Store::writable_parent`, `home_of`), as /guest is anyone's to write in. `protect_home` ignores guest's home for homes inside it.
- Commands (owner's request, 2026-10-27) are defined once, for clap, in core `cli/` (one module per manual section): a `#[derive(Parser)]` struct whose doc comment is the summary and description and whose fields' docs are the options, plus `impl Manual` for the section, needs, examples and see-also; each is listed in `cli::DEFINITIONS`. Parse arguments with `cli::parse::<T>`, never by hand: its errors are clap's, on one line ("NAME: reason; NAME -h shows how to use it"). `-h`/`--help`, `help` and `man` pages are generated from the definitions (`cli::help`, `cli::page`, `cli::index`; man gets its pages through `window.terminalManual`); `-h` is help unless the command defines a short `-h` of its own and has more arguments, or runs with `-h` alone (`df -h`) (`cli::wants_help`). Running a command is a program of user space (crates/userland `run`, over the system calls) or a `TerminalCommand` in frontend `shell/commands.rs` (what needs the page: open, upload, stream, present, cd, filters); a defined command with neither is sent to app.js's `accountCommand`, for its dialogs. A new command is a definition and a program (or a terminal entry); what the kernel must decide is a system call.
- `faststart FILE` is an archive job (`Job::Faststart`): the runner's `create` sends the file as input 0 and calls the container's `POST /faststart` (`crates/jobs` `faststart.rs`, a qt-faststart-style relocation) instead of `/build`, then writes the result over the file in place (`replace`). A 422 from the container ends the job with one error line, not retries; `already` ends it without writing. The upload warning for non-faststart MP4s points to it.
- Archive output must stay deterministic (pinned mtime, owners from the snapshot, miniz_oxide at a fixed level, fixed gzip header bytes): a resumed `zip`/`tar -c` rebuilds and compares chunk SHA-256s with what is stored, and starts the upload over on any difference. A change to the job container that changes bytes is fine only because of that check; keep it.
- Extraction follows Linux: members written in place one by one, unsafe ones (`..`, devices, duplicates) skipped with a warning (core `archive::member_path`), a cancelled or interrupted member's upload cancelled so no partial file remains. unzip's replace question is asked once, for all conflicts, before writing (`state = question`). Links in archives: members `symlink`/`hardlink` (`crates/jobs` `Kind`), planned with their target in `plan.link`; symbolic links are made in a second pass after all other rows. Replacing a file during extraction unlinks it first (`/internal/job/begin` with `unlink`), so no per-file chmod follows; `tar -c` over an existing archive still writes the inode in place. Job probes (`/internal/job/exists`, `begin`) check traversal before looking at a node, as `cp`/`mv` destinations do, each one of a recursive copy's merge included (`Store::copy`). The runner's KV key `planned` says planning finished, so an empty plan ends the job rather than plan again; error counts carry over from planning and earlier steps via the job's progress. Modes (`runner::extracted_mode`): unzip the archived bits, tar those less 022, or for root all of them, 000 included (`Member.mode` is `None` when a zip has none: 644/755); a file gets its mode at `begin`; directories, at the end, whenever their current mode (from `exists`' `modes`) differs, those that were there before too. `jobs::view` pages 500 lines with `more`; the shell drains every page before treating a job as ended. Guests' jobs act as guest.
- Owner/group/other select exactly one class, without bit union or fallback. Root uid 0 retains complete control. Check all ancestor x bits before inspecting protected contents.
- Authorize HEAD, Range, and conditional requests before returning data or 304. Keep private/no-store, Vary Cookie, nosniff, and file-response sandbox/CSP behavior; SVG is served as `image/svg+xml` only because of that sandbox and its `Content-Disposition: attachment`.
- File creation needs parent w+x; overwriting needs file w; deletion needs parent w+x. Recursive operations validate the entire affected tree before mutation.
- Some HTTP error classification currently matches English message fragments. Preserve 401/403/404/409 semantics when editing messages; permission/API tests cover these paths. A future typed-error refactor must preserve behavior.

## Required account semantics

These were explicitly chosen by the owner; do not silently replace them with full Linux semantics.

- guest cannot sudo. Normal sudo callers must belong to **wheel**, not a sudo/sudoers group. Root keeps full control.
- `sudo COMMAND` elevates only that request. The five-minute credential cache is used only for explicit sudo requests, with membership rechecked each time.
- `su [-] USER` switches accounts using the target password; root may switch to an enabled account without it.
- `sudo -u USER` switches the browser account and enters its home. It does not accept a trailing command.
- `exit` and `logout` revoke the session and return directly to guest at /. No nested account stack.
- Permission checks must never implicitly log guest or a normal account in as root.
- `passwd --force` skips only the 12-character minimum. It still requires a nonempty password, at most 512 bytes, and normal identity/authorization checks.
- Account changes revoke old sessions; a self-password change issues a new current session. Locking revokes sessions. Unlocking does not resurrect them.

## UX requirements and fragile areas

- Main text is 20px.
- The desktop (owner's request, 2026-10-30: "a windows compositor … should not draw directly on canvas, it calls browser api … These should be wasm"; step 1 of the plan toward init, a greeter, a kernel of processes and outside GUI apps).
  - `crates/frontend/src/desktop.rs` lays out DOM windows (`.window`, `data-window`, one of `APPS`) absolutely within `.desktop-area`, by inline style (left, top, width, height, z-index 20 + rank), from `Desktop.windows`. Frames are kept per browser in localStorage `terminal-desktop`.
  - The viewer's and editor's `<dialog>`s are adopted: moved into the area, given handles and buttons, and followed by their `open` attribute. They open with `show()`, never `showModal()`; a closed dialog is not marked `window-hidden`, so it can take the focus the moment it opens.
  - Only the sign-in dialog is modal. "A dialog is in the way" is `dialog[open]:modal`; "another window has the keyboard" is `.window:not(#window-terminal)` (app.js `restoreTerminalFocus`, the typing redirect). The Files window takes focus (`tabindex=-1`), so a click there keeps the keyboard there.
  - Up to 650 px wide (`COMPACT`, as the CSS), one window shows at a time, filling the area; there is no maximize button.
- Restrained colors, line icons, highlighted prompts, and ls-style listings are intentional. Terminal scrollbars are hidden, but scrolling must work.
- Completion takes from each command's clap definition which operands and option values are paths (`value_hint`: `DirPath` for directories, `AnyPath` otherwise; core test `path_operands_say_so_for_completion` fails for a path operand without one). Completion is fish-like: the first Tab only lists the fuzzy candidates (owner's request, 2026-10-28: so that more may be typed to narrow them), unless there is one, which completes at once (`CompletionSession::selected` is `None` until one is picked); Tab and Shift+Tab then cycle the original candidates, empty input browses files, quoting and Unicode are preserved, and stale asynchronous results are discarded.
- Every command has -h / --help, from its clap definition, as is its man page. Help must run before authentication or side effects (the shell answers it before dispatch). Respect -- when interpreting help flags.
- Wildcards (owner's request, 2026-10-26) expand as bash expands them: in the page, per stage as it starts (`Shell::expand`), listing with the caller's permissions; matching and quoting rules are in core (`glob.rs`, `shell::words`). Items xargs reads and fd -x placeholders are never expanded, as in a shell.
- Live changes (owner's request, 2026-10-26): every page keeps a WebSocket to the authority (`/api/events`, origin-checked in the Worker, hibernatable, pings auto-answered). `Db` notes the directories a committed transaction changed (`set_node`, `delete_node`, chunk commits); the authority sends each socket only those its session's account may list (READ|EXEC), after every request and after the alarm. Node writes must keep going through `set_node`/`delete_node` so that they are heard. Pages send one thing on it (owner's request, 2026-10-28): `{"present": {"path", "at": [column, row]}}`, the slide or presented PDF page they show (`terminal.present`, from viewer.rs); `TerminalAuthority::relay` passes it to the sockets of the same account in other sessions (other browsers; never for guest), and the windows of one browser hear it from each other (`BroadcastChannel('terminal-present')`); app.js turns both into `terminal:present`, which the deck or PDF showing that path follows without saying it again.
- Uploads: the file chooser opens synchronously in the gesture (`Shell::run` calls `terminal.chooseFiles()` before anything is awaited; phones refuse it later); Ctrl+C or closing the tab settles a chooser still open with no files (`cancelChoosing`), as a browser may close one without a cancel event. Dropped files go to the active tab. Progress is a live line in that tab's transcript; there is no page-level notice. Progress, there and in listings (`Entry.uploaded`, `Db::received`), is the bytes of the committed chunks, wherever they are; `Db::readable`, the prefix readers get, is for reading. One descriptor writes a file at a time (owner's request, 2026-10-27): the uploading page keeps it (`lease`, upload.mjs) and closes it when it stops or goes; another page goes on with the same file only once it is closed or `fds::LEASE` passed, and the old descriptor then writes no more. Archive jobs write without descriptors, until processes (phase 5). EBADF (409) on a chunk means the upload is gone (removed elsewhere) or went on from another page: this page stops.
- Phones (≤650px): a fixed, full-screen app sized by `--app-height`/`--app-top` from `visualViewport` (app.js), `.keyboard` while the on-screen keyboard is open; touch keys (Tab ↑ ↓ ^C) on coarse pointers. Keep inputs at 16px or more, or iOS zooms.
- Escape with a dialog open is the page's (app.js): it prevents the default, which Safari would use to leave a full-screen window, and dispatches `cancel` to the dialog, whose own handler closes it. Handlers inside a dialog that take Escape first (preview search, CodeMirror) prevent it, and are left alone; element fullscreen keeps the browser's Escape.
- Viewer: links in previews call `terminal.follow`, which keeps a trail for Back; `terminal.place`/`setPlace` keep where each file was left (slide, PDF page and zoom, scroll, media time) in localStorage. PDFs are one scrolling document drawn lazily by IntersectionObserver; canvases sit absolutely in their frames so drawing never resizes the layout. Slide themes are `.slides[data-theme]`, for slides only. Image-only slides are marked `.slide-image` by `preview::image_slide`; they fit the available area without text-slide zoom, padding or the 460px illustration limit. Keep ordinary slides with captions or headings on the text layout. Slides (owner's choice, 2026-10-28: the simplest reveal-style player of Markdown, nothing fitted to HTML decks) are drawn by `Stage`, which keeps every slide that came within two of the one shown mounted and hidden (files are no-store: a slide drawn again would fetch its images again), so tests find the slide shown as `.slides-current .slide:visible`; each stage sets its own `--scale`. `preview::slides` returns each slide's HTML and its notes (from `Note:`). The speaker view is the same component with `.slides.speaking`; S opens it in a pop-up at `/?speaker=PATH`, which app.js's `started` opens. Slides focus their body when shown, as the dialog focuses its first link; `pressing` leaves Space and Enter to a button or link tabbed to, and app.js keeps a click on a viewer button from taking the focus. Escape for the overview or an enlarged image is taken in the capture phase, before app.js's dialog Escape. PDFs present one page at a time (`present` in their place), with their scrolling stage hidden.
- /dev (owner's design, 2026-10-29; `crates/worker/src/dev`, core `devices`, web/dev.mjs): devices are character devices, nodes of their own (`Node::rdev`, the inodes' `rdev` column, `S_IFCHR`), made by `mknod` with `rdev` (`dev::mknod`: in the driver's directory, signed in, a name free or the caller's, which replaces it), with the mode a file gets and the ACL their maker gives them; the `devices` table is their drivers' state (owner, path shown, `media` for a sound). Who may read (follow, hear, ask to speak) or write (show, turn, speak, send) is their mode's and ACL's to say, checked by the kernel (`kernel::open`, `dev::followed`); what they do is their driver's: `dev/present.rs` (`PRESENT_SHOW`, `PRESENT_ASK`, `PRESENT_ANSWER`, `PRESENT_SPEAK`), `dev/snd.rs` (`SND_PUBLISH`, `SND_LISTEN`, `SND_ANSWER`), as `ioctl`s on descriptors that open them (fds' `device` column); those that ask Realtime are decided in a transaction, asked outside, and recorded in another (`sys::networked`). Reading one (`GET /api/file`, `cat`) gives its state as JSON (`dev::read`). Removing one (`rm`, its account or root; stop; expiry; userdel) hangs it up (`dev::hangup`), revoking its descriptors, and its followers and its account's pages hear so after commit (`db::take_removed`). A presentation is turned by its account and those its mode or ACL let write it (`present::turns`; root only what it presents), through the socket's `present` places, kept per (owner, path). Asks are the driver's (`asks` table, per session; withdrawn when the session's last line goes); its news goes to the pages it is for after commit (`db::tell`, `Told::Account` or `Told::Session`, `store::tell`). Allowed, an account gets `u:NAME:rw` on the presentation; a guest's session a write descriptor passed to it (`granted.fd`). Voices are /dev/snd devices of the presenter, with the presentation's mode and ACL, made through the speaker's descriptor (`present::spoken`), ending when it closes or is removed, which takes the leave to speak back (`present::silenced`). A sound lasts while the descriptor that sends it is kept and open (`dev::leased`, `snd::closed`). The socket's `follow` is the watch of devices; its lines know their session (`Line.sid`, the browser's own signed out, so the page opens its line after its first request has given it its cookie).

- Recordings (`stream`, web/record.mjs): a new file opened `O_WRONLY | O_CREAT | O_EXCL | O_APPEND` (a file in state `recording`, size 0, chunk size `api::RECORDING_CHUNK`); it takes only its next chunk, whole or (last) short, and its size and its nodes' grow as each commits (`Db::grow_file`). `stream -m ENTRIES` gives it, and its live sound, their ACL as they are made (user space's setfacl, `terminalUploads.setfacl`); entries it cannot take remove what was made. Its lease keeps it alive; unkept for `api::RECORDING_IDLE`, the alarm completes it with what arrived (`api::finish_recording`), and so does closing its descriptor (`jobs cancel fdN` from another tab of the browser). It takes no chunk past `api::RECORDING_MAX`; the page then closes it. Listings mark it `recording`. Browsers record Opus in WebM only, so recordings are `.weba`.

The authority decides, then calls Realtime with the secret: the speaker's page offers its microphone track (`voice`) in a session of its own, kept as the device's `media`; a listener gets a session pulling that track, which it answers (`SND_ANSWER`). The player (`#listening`, app.js `hear`) moves into the viewer while it is open, to show over it; the `<audio>` stays outside so moving never stops it. Listening has a rate limit of its own (`LISTEN_LIMIT`, 300 a minute per address), as a room of listeners may share one address. A listener's connection that fails once made is heard again (`AGAIN`, app.js), while the device may be heard. `stream` names its sound after the account unless `-n` names it.
